# Special characters & umlauts

Reported by a German user: incoming MeshCore messages often contain umlauts
(`ä ö ü Ä Ö Ü ß`) and symbols like `°`, which the client could neither display
nor type. This feature has two independent halves.

## A. Display — extended Montserrat font

We render chat with the stock LVGL built-in Montserrat faces
(`lv_font_montserrat_14/16/20/22/24`, chosen in `mc_font()` in
`components/mc_ui/lvgl_ui.c`). Those faces only cover **ASCII + `°` (U+00B0) +
`•` (U+2022)** — every accented Latin letter renders as the missing-glyph box,
so umlauts in *received* messages are unreadable regardless of how they were
typed.

Fix: ship our own extended faces `lv_font_montserrat_<sz>_ext`, generated from
the same `Montserrat-Medium.ttf` LVGL bundles, covering:

| Range | Contents |
|---|---|
| `0x20–0x7F` | ASCII |
| `0xA0–0xFF` | Latin-1 Supplement — umlauts, accents, `° § µ ¿ ¡ « » ß æ ø …` |
| `0x2013–0x2014` | en/em dash |
| `0x2022` | bullet (kept from the stock face) |
| `0x20AC` | euro `€` |

This covers German, Nordic, French, Spanish, Portuguese and Italian text.
Central/Eastern European letters (Polish `ł`, Czech `č/š/ž`, …) live in Latin
Extended-A and are a later expansion if requested.

### Regenerating the font

```sh
scripts/gen_ext_fonts.sh      # needs Node's lv_font_conv; NAS CI image has Node
```

Output lands in `components/mc_fonts/lv_font_montserrat_<sz>_ext.c` (checked in
as generated asset data, like `emoji_bitmaps.c` — do not hand-edit; both have a
generator under `scripts/`).

### Wiring (implemented)

The generated faces live in the `mc_fonts` leaf component
(`components/mc_fonts/`): the five `lv_font_montserrat_<sz>_ext.c` files plus
`mc_fonts.h` which `LV_FONT_DECLARE`s them. `mc_font()` in `lvgl_ui.c` returns
the `_ext` faces, and `mc_ui` pulls `mc_fonts` in via `PRIV_REQUIRES`. The stock
built-in Montserrat faces stay enabled in sdkconfig (LVGL's default style still
references `lv_font_montserrat_14`); ours are additive.

Flash cost is essentially neutral: once `mc_font()` stops referencing the stock
built-in Montserrat faces the linker garbage-collects them, and our `_ext` faces
(generated with `--force-fast-kern-format`) are slightly more compact. Measured
on the tanmatsu target: the full feature builds to `application.bin` = 0x1b29d0
(1,779,152 B), which is ~8.6 KB *smaller* than the picker-only build with the
built-in faces (0x1b4760), leaving 15 % (0x4d630) free in the 2 MB app
partition. Confirm on hardware that an incoming `ä/ö/ü` message and the `€`/`°`
signs render.

## B. Input — F5 "blue cloud" special-character picker

Mirrors the F4 emoji picker exactly. While typing in a chat/channel:

- **F4 (green circle)** opens the emoji bank (bitmaps).
- **F5 (blue cloud)** opens the special-character bank (font glyphs).

D-pad / WASD move the cursor, RETURN inserts the character's UTF-8 bytes into
the input buffer, red X (F1) or pressing F4/F5 again closes the overlay. One
overlay serves both banks; `emoji_picker_mode` (`PICKER_EMOJI` / `PICKER_SPECIAL`
in `chat.h`) selects which, and the UI drives it through `picker_count()` /
`picker_entry()` so no call site branches on the mode.

### Typing directly with AltGr

The picker is not the only way in. The Tanmatsu BSP keyboard event carries a
UTF-8 string (`args_keyboard.utf8`) next to the ASCII byte, and the driver
already fills it with the **AltGr** (`ALT_R`) variant of a key when AltGr is held
(`handle_keyboard_text_entry` in `badge_bsp_input.c`). `handle_key()` now takes
that `utf8` pointer and, in the text-input paths, inserts it directly when it
decodes to a font-covered character (`insert_altgr_utf8`). So a user can type
`ä` with AltGr instead of opening the picker. This is wired for **chat/channel
typing** and **free-text settings fields** (e.g. the node name — "Jürgen");
restricted fields (region scope, BLE PIN) and channel names stay ASCII, the
latter because the name feeds the channel-key hash.

### The 40-character bank

Frequency-ordered into the same 4×10 grid the emoji picker uses (German first,
then Nordic, Romance, punctuation). Defined in
`components/mc_common/special_table.c`, generated by
`scripts/gen_special_table.py`:

```
ä ö ü ß   Ä Ö Ü °   € § µ ñ   é è ê ë   à â á ç
î ï í ô   û ù ú ó   å Å æ Æ   ø Ø ¿ ¡   « » – —
```

All are Latin-1 Supplement except `€` (U+20AC) and the en/em dashes (U+2013/14),
which the extended font (part A) also covers.

The bank is unit-tested on the host (`tests/test_special_table.c`): every entry's
`utf8_len` matches its bytes, `utf8_decode` round-trips to the declared codepoint,
and there are no duplicates.

> **Note:** B depends on A — an inserted `ä` only renders once the extended font
> ships. The picker code and table land first; the glyphs light up when the font
> is wired in.
